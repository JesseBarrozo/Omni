- Phase Harness Swap : `omni swap --conversation ID --harness codex|claude` crée un checkpoint persistant, inclut l’historique et l’état Git dans le contexte de reprise, bloque les tours/outils/permissions actifs et crée une session via l’adaptateur réel. Le parcours réel Codex → Claude → Codex est passé sur un projet Git temporaire; détail dans `VERIFICATION.md`.
- Phase Auto Orchestrator : `omni run --auto` construit son registre depuis les catalogues réellement exposés par les comptes Codex/Claude authentifiés, classe déterministement les modèles/harness compatibles, journalise candidats/exclusions/critères/secours/résultats et utilise les résultats précédents entre conversations. Si l’initialisation du harness échoue avant que le prompt soit enregistré ou qu’un tour commence, Omni prépare le candidat suivant et consigne `routing.fallback`; après le début d’exécution aucune relance automatique n’est possible. Le parcours réel Codex préflight indisponible → secours Claude OAuth → réponse terminée est passé. Les limites de prix/confidentialité et les commandes de test sont explicites dans `README.md` et `VERIFICATION.md`.
- Compatibilité Orca vérifiée sur la CLI/runtime installée : Omni peut être utilisé comme commande ordinaire dans un terminal Orca existant. `orca agent launch --agent omni` renvoie `Unknown TUI agent "omni"`; aucune interface publique de registration d’agent externe n’est exposée. Aucune modification du code ou des réglages Orca n’a été faite; détails et commandes supportées dans `ORCA_COMPATIBILITY.md`.
- Investigation Antigravity OAuth : la CLI officielle `agy` a répondu à une requête réelle avec un modèle de son catalogue via son authentification locale (sans clé API/ADC transmise dans l’environnement). Le compte OAuth actif n’a pas pu être confirmé séparément. L’interface headless ne fournit pas de callback de permission pour Omni et autorise les écritures dans l’espace de travail par défaut; même `--mode plan` expose des outils mutateurs. Aucun adaptateur Omni n’a donc été ajouté, afin de ne pas contourner les permissions. Preuves et limites dans `VERIFICATION.md`.
- Auto chat : les demandes classées sans outils peuvent choisir les vrais catalogues OAuth Codex/Claude et sont streamées par leurs adaptateurs de chat. Le routeur classe d’abord les options sans outils et ensuite l’adaptateur Codex en lecture seule; les tâches avec outils restent sur un harness avec permissions. Le parcours réel Auto a validé Codex chat et l’autre test live continue de valider le fallback vers Claude harness.
- Provider/Model Registry : migration SQLite version 2 pour conserver fournisseurs, état d’authentification/catalogue, modèles, disponibilité et préférences d’activation. `providers refresh|list|enable|disable` et `models list|enable|disable` utilisent les catalogues réels Codex/Claude et l’API OpenAI uniquement si sa clé est configurée. Le mode Auto respecte les états persistés. Aucun secret n’est enregistré; les comptes multiples ne sont pas encore pris en charge.
- Harness Registry : migration SQLite version 3, inspection et rafraîchissement non-exécutant des adaptateurs réels Codex app-server et Claude Agent SDK, persistance de leurs capacités et disponibilité, et contrôle enable/disable appliqué à Auto, `run` et `swap`.
