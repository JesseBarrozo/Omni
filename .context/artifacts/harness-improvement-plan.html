Written for: l'équipe Second Brain (développeurs qui utilisent Claude Code et Codex sur ce dépôt). Projet analysé : second-brain-1.4.0.

Plan d'amélioration du harness

Le « harness » ici désigne tout ce qui cadre l'agent IA sur ce dépôt : instructions (AGENTS.md/CLAUDE.md), skills, configuration MCP, permissions, hooks, sous-agents, et les contrôles qui valident un changement.

Périmètre révisé. Ce dépôt sert de base de départ et n'est pas utilisable en l'état. Le projet ne fera aucun appel à Hostinger ni à Invokta.

Résumé. Le socle est bon : une seule source d'instructions, des règles d'architecture précises et une CI qui exécute typecheck, tests et build. Les faiblesses se trouvent surtout côté Claude Code et côté application des règles. Les règles d'AGENTS.md ne sont pas imposées par la configuration. Rien n'empêche une session de finir sans npm run check. Le skill de développement n'est pas dans l'emplacement que Claude Code lit. Enfin, un serveur MCP est lancé sans version épinglée.

  • Aucun .claude/ partagé : pas de settings.json, pas de permissions, pas de hooks, pas de sous-agents.
  • Le skill develop-invokta-project vit dans .agents/skills/ (format Codex). Claude Code ne le découvre pas.
  • Un MCP hostinger-vps est configuré, et le framework @invokta/* est au cœur de l'engine. Décidé : Hostinger est retiré, Invokta sera retiré (phase R).
  • Le dépôt n'est pas un dépôt git dans ce dossier, et node_modules est absent : aucune vérification locale n'est possible sans installation.

2. Plan d'implémentation

Phases 0 à 4, plus la phase R (retrait d'Invokta). Chaque phase est indépendante et réversible, sauf indication contraire.

Phase 0 : Base vérifiable

~30 min
  1. Exécuter npm ci puis npm run check à la racine. Noter l'état de référence (vert ou non) avant toute modification.
  2. Auditer les appels sortants : recenser les fetch et les hôtes dans apps/, puis documenter la liste blanche. Les API des fournisseurs LLM sont autorisées ; les autres hôtes sont à confirmer. Ce dépôt de base n'est pas la cible : on part de son code pour le nôtre.
  3. Ajouter .DS_Store à .gitignore et retirer le fichier du suivi s'il est versionné.
  4. Documenter dans AGENTS.md les commandes par workspace et le prérequis Docker pour test:postgres.

Phase 1 : Sécurité et configuration partagée

~2 h
  1. Supprimer l'entrée hostinger-vps de .mcp.json et de .codex/config.toml. Supprimer .mcp.json s'il ne contient plus rien.
  2. Créer .claude/settings.json (versionné) avec des permissions minimales : autoriser les scripts de lecture et de test (npm run typecheck, npm test, npm run check) ; demander confirmation pour git push, rm -rf et les commandes npm publish ; interdire la lecture de .env*.
  3. Déplacer tout réglage personnel vers .claude/settings.local.json, déjà ignoré par Git.

Phase 2 : Un seul emplacement pour les skills

~1 h
  1. Garder .agents/skills/ comme source canonique, puisque Codex le lit déjà.
  2. Exposer le même contenu à Claude Code via un lien symbolique .claude/skills → ../.agents/skills. Vérifier que Claude Code le détecte dans une session neuve.
  3. Corriger la description du skill et openai.yaml pour désigner notre projet, et non « Invokta » ni « Second Brain ».
  4. Ajouter un skill second-brain-mcp côté dépôt si le contenu de apps/admin/src/content/agent-resources/ doit aussi guider les agents qui travaillent sur le code.

Phase 3 : Faire appliquer les règles

~half-day
  1. Hook Stop : si des fichiers ont été modifiés pendant la session, lancer le typecheck du workspace touché et bloquer la fin tant qu'il échoue. Garder un garde stop_hook_active pour éviter les boucles.
  2. Hook PreToolUse sur Edit|Write : demander confirmation pour apps/engine/src/http-auth.ts, direct.ts et mcp-http.ts, les trois fichiers protégés par AGENTS.md.
  3. Hook SessionStart : si node_modules est absent, lancer npm ci et l'annoncer dans le contexte.
  4. Transformer en tests les règles mécaniques : parité des clés en.ts / pt-BR.ts / es.ts (déjà couvert par le type Catalog, à confirmer), et parité des titres entre docs/*.md et docs/*.pt-BR.md.

Phase 4 : Sous-agents de revue

~2 h
  1. .claude/agents/contract-reviewer.md : vérifie les identifiants de capacités, schémas, accès et annotations contre le snapshot de la phase R, en lecture seule.
  2. .claude/agents/i18n-reviewer.md : repère le copy en dur dans les composants de apps/admin/, en lecture seule.
  3. .claude/agents/docs-sync.md : signale les documents en anglais modifiés sans leur traduction pt-BR dans le même changement.

Ces sous-agents n'ont que des outils de lecture. Ils ne modifient jamais le code.

Phase R : Retrait du framework Invokta

~1 à 2 jours

Décidé. Peut suivre la phase 0. Les phases 3 et 4 et l'atlas s'appuient sur son résultat.

  1. Inventaire. Lister chaque import @invokta, chaque test, script et fichier généré. Points connus : engine.ts, mcp-http.ts, http-auth.ts, apps/server/src/services/admin/engine.ts, admin-access.ts, une vingtaine de tests.
  2. Figer la référence. Extraire de invokta.mcp.json un snapshot des 64 capacités : identifiant, schémas d'entrée et de sortie, accès, délai. Ce snapshot devient le contrat de compatibilité, à ne pas modifier pendant le retrait.
  3. Tests d'abord (RED). Un test compare le snapshot au registre. Un second échoue tant que @invokta reste dans apps/*/src ou dans les manifestes.
  4. Remplacer le noyau (GREEN). defineCapability et engine.invoke deviennent des modules du projet, avec les mêmes signatures. Les règles d'AGENTS.md restent : un seul chemin engine.invoke, pas de registre global, pas de chargement dynamique.
  5. Transport MCP. Remplacer le transport d'mcp-http.ts par le SDK MCP officiel, sans logique métier dans le fichier. direct.ts reste une simple entrée.
  6. Adapter le serveur. Porter apps/server/src/services/admin/engine.ts et admin-access.ts sur le nouveau module.
  7. Supprimer l'outillage. Retirer les dépendances @invokta/* de apps/engine/package.json et apps/server/package.json, puis régénérer le lock avec un seul package-lock.json. Supprimer invokta.mcp.json, apps/engine/invokta.deploy.json et deploy/healthcheck.mjs. Retirer les scripts check:mcp, devtools*, deploy:probe. Mettre à jour release-please-config.json, le Dockerfile (copie de invokta.mcp.json) et deploy/DEPLOYMENT.md.
  8. Vérifier. npm run check vert, snapshot inchangé, et grep de @invokta vide, hors CHANGELOG.md et l'historique git.

3. Atlas du projet : un second brain pour les agents

Objectif : donner aux agents une carte vérifiée du dépôt, pour qu'ils trouvent vite le bon fichier et répondent sans inventer de noms, de capacités ni de variables d'environnement. L'atlas est versionné dans le dépôt, généré à partir du code quand c'est possible, et testé contre lui. Il ne remplace pas le second brain produit (le runtime MCP) : c'est une mémoire de développement pour les agents qui modifient ce code.

Principes

  • Vérité par le code. Tout ce qui peut être extrait du code l'est par un générateur : capacités, schémas de données, variables d'environnement, carte des workspaces. Un humain ne recopie rien à la main.
  • Chaque affirmation cite sa source. Format apps/engine/src/capabilities/tasks.ts:42. Un contrôle vérifie que la référence existe encore.
  • Dire « inconnu » plutôt qu'inventer. Si un point n'est pas documenté ou pas trouvable dans le code, l'atlas le marque non documenté, et les agents doivent répondre de la même façon.
  • Chargement progressif. Un point d'entrée court (atlas/README.md) est lu en premier. Les pages détaillées ne sont ouvertes qu'à la demande, pour garder le contexte léger.
  • Neutralité fournisseur. Aucune page ne cite un modèle, un format de prompt ou une fonctionnalité propre à Anthropic, OpenAI, Google ou un autre fournisseur. Les pages sont du Markdown et du JSON, avec des liens relatifs.
  • Budget de contexte. Les fenêtres de contexte varient selon les modèles. Le point d'entrée reste court, et chaque page se lit seule, sans import implicite.
  • Anglais. Selon AGENTS.md, le contenu du projet est en anglais. L'atlas suit cette règle, même si le plan est rédigé en français.

Mécanismes anti-hallucination

  1. Génération reproductible. tools/atlas/generate.mjs réécrit les pages générées. Une exécution sans changement de code ne doit produire aucun diff.
  2. Contrôle de dérive. npm run atlas:check régénère, compare et échoue si un fichier généré n'est pas commité. Il vérifie aussi que chaque chemin:ligne cité existe, et que la liste des capacités du snapshot égale celle enregistrée dans engine.ts.
  3. En-tête de fraîcheur. Chaque page générée indique le SHA du commit et le hash des sources utilisées.
  4. Consigne dans AGENTS.md. Une ligne : « Avant d'affirmer un nom, une capacité ou une configuration, consulter atlas/README.md ; si l'atlas ne le contient pas, lire le code et signaler le gap. »
  5. Adaptateurs optionnels. Un hook SessionStart (Claude Code), ou l'équivalent d'un autre outil, peut injecter le résumé de atlas/README.md. Ce n'est jamais une condition de correction : sans lui, l'agent lit AGENTS.md puis l'atlas.
  6. Mise à jour neutre. La logique vit dans tools/atlas/, en scripts Node sans appel à un modèle. Un sous-agent atlas-keeper n'est qu'un adaptateur par outil : il appelle ces scripts et écrit dans atlas/.

Phases de réalisation

  1. A. Générateurs (~1 jour) : capacités, schéma de données, configuration, map. Sortie : pages générées et index.json.
  2. B. Pages manuelles (~half-day) : README, recipes, glossary, chaque affirmation sourcée.
  3. C. Contrôles (~half-day) : atlas:check branché sur npm run check et sur la CI.
  4. D. Câblage agent (~2 h) : ligne dans AGENTS.md, hook SessionStart, sous-agent atlas-keeper.
  5. E. Évaluation (~half-day) : 20 questions avec réponses attendues et sources (« Quelle capacité crée un rappel ? », « Quelle variable active le mode OAuth ? »). Rejouer le même jeu avec chaque fournisseur retenu, et mesurer le taux de réponses inventées avec et sans atlas, avant de considérer l'atlas utile.

Point à vérifier : le générateur peut s'appuyer sur l'API du compilateur TypeScript. Il faut confirmer qu'elle est disponible dans les workspaces, sinon l'ajouter comme dépendance du workspace concerné.

5. Décisions

Tranchées par l'équipe, en suivant les recommandations. Une question reste ouverte.

  1. Framework Invokta : retiré. Décidé. Réalisé par la phase R. Le serveur MCP passera par le SDK officiel ; ce choix reste à confirmer au moment de l'implémentation.
  2. Appels sortants : API des fournisseurs LLM autorisées. Décidé pour OpenRouter, Anthropic, OpenAI, Google et les autres fournisseurs de modèles. Ouvert : Slack, Telegram et la publication de release. Sans réponse, ces hôtes restent interdits.
  3. Trois fichiers protégés : confirmation demandée. Décidé. Le hook PreToolUse demande une confirmation, sans bloquer.
  4. Hook Stop : typecheck en fin de session. Décidé. Le check complet reste en CI.
  5. Atlas dans le dépôt. Décidé. La publication comme pack pour les clients MCP viendra après la phase E, avec un accord séparé.
  6. Fournisseurs évalués : Anthropic et OpenAI d'abord, Google si le budget le permet. Décidé.
  7. Seuil de réussite : moins de 5 % de réponses inventées, et 100 % de citations valides. Décidé, sur les 20 questions de la phase E.

6. Vérification

Ce plan est fondé sur la lecture des fichiers. Je n'ai pas exécuté npm run check : node_modules est absent. La phase 0 doit établir l'état de référence avant toute modification.

  • Après la phase 1 : ouvrir une session neuve, vérifier qu'aucun prompt ne demande npm run check, et que le MCP démarre avec la version épinglée.
  • Après la phase 2 : vérifier que le skill apparaît dans la liste des skills de Claude Code.
  • Après la phase R : npm run check vert, snapshot des 64 capacités inchangé, et aucun @invokta restant hors historique.
  • Après la phase 3 : introduire volontairement une erreur de type et confirmer que le hook Stop bloque la fin de session.
